## Мои машины и сеть T3 (mesh)

На каждой машине работает свой T3 Code Sidebar. Вместе они — **сеть (mesh)**:
серверы связаны друг с другом, у всех одна раскладка сайдбара (воркспейсы,
порядок, метки машин, логические проекты), и правка на любой машине доходит до
остальных за секунды.

| Машина | Метка | Что это | Как достучаться отсюда |
|---|---|---|---|
| gvidon | GV | Главная машина: мощная, здесь живут `.git`, сборки, тесты, docker большинства проектов. Claude здесь не работает (забанен), Codex/DeepSeek — да. | с Operalia: `ssh gvidon`; с gor: туннель `t3-gvidon-tunnel` |
| Operalia | OP | VPS `138.249.138.105`, здесь работают Claude-агенты. | с gvidon: `ssh operalia` |
| gor | GOR | Вторая машина дома (`gor.local`, Ubuntu, 32 ядра, 125 ГБ). Тестовый стенд T3: обновлять и перезапускать можно. | с gvidon: `ssh -F ~/.local/share/gor-transfer/ssh_config -i ~/.ssh/id_malaniya_25519 -o IdentitiesOnly=yes gor` |

Метки и имена машин настраиваются в T3 (Настройки › Mesh); список выше — как
сейчас.

**Как действовать.** Перед действием с T3 прочитай скилл `t3` и используй его команду, если она покрывает просьбу. Точные имена машин, метки и пути бери из `t3ctl machines` и `t3_project_machines` (таблица выше — физические машины, на стенде их может быть больше). Тред ищи сразу на всех машинах (`t3ctl find "…" --all`), сравнивай по смыслу заголовка: просьба может быть по-русски, а заголовок по-английски. Найденный тред открывай через `ui_open` с полными `threadId` и `environmentId`. Для файловой операции сначала получи представления проекта и выбери целевую машину и сформируй абсолютный путь в её представлении. Текущая папка и primary из контекста реплики не заменяют эту цель. В реплике даже `git status` запускай на primary через ssh: первоначальная проверка состояния выполняется там же, где и сама операция.

**Логический проект** — одна карточка в сайдбаре, а у неё представления на
машинах:
- **primary** — своя копия с `.git`, там идут git, сборки и тесты; их может быть
  несколько;
- **replica** — рабочая копия, которую Mutagen синхронизирует с primary
  (без `.git`, `node_modules`, `.venv`, `dist`, `build`, `.t3`).

Если ты работаешь в реплике: файлы правь здесь, а git, сборки, тесты и docker
запускай на primary — `ssh <машина> 'cd <путь> && <команда>'` (T3 добавляет
точную команду в контекст треда). Никогда не делай `git init` и коммиты в
реплике.

**Работа с T3 на любой машине — скилл `t3` (CLI `t3ctl`).** Машину называй как
угодно: «гвидон», «опералия», «гор(а)», метка или id — `--on <машина>`.

| Что я прошу | Что делать |
|---|---|
| «создай тред в проекте X на Operalia (на соннете…)» | `t3ctl new --project X --on operalia [--agent/--model] "задача"` — если проекта там нет, T3 сам поставит реплику, дождётся синка и запустит тред |
| «сделай X репликой на горе» / «поставь X на M» | `t3ctl place X --on gor [--wait]` |
| «открой тред про …» | `t3ctl find "…" --all`, затем `t3ctl open <тред>` (или `ui_open` с `environmentId`) |
| «что сейчас работает на всех машинах» | `t3ctl status --all` |
| «покажи файл … из X на гвидоне» | `t3ctl cat <путь> --on gvidon` / `t3ctl open-file <путь> --on gvidon` (или `ui_open` с файлом и `environmentId`) |
| «какие у меня машины», «что в сети» | `t3ctl machines`, `t3ctl mesh status` |



Из треда T3 то же самое доступно MCP-инструментами `t3-code` с параметром
`environmentId` (`t3_thread_launch`, `t3_thread_search`, `t3_project_place`,
`t3_project_machines`, `ui_open`). Связывать и отвязывать машины, удалять
реплики — только по моей просьбе.

## Голосовые звонки в T3

- В T3 есть MCP-инструмент `voice_control`: по моей просьбе «выключи микрофон»
  или «перестань слушать» вызывай его с `action: "mute"`. Звонок остаётся открыт;
  включить микрофон обратно могу только я кнопкой на своём устройстве.
- По просьбе «останови/заверши звонок» коротко подтверди и вызови
  `voice_control` с `action: "end"`. Тред и история сохраняются.
- Эти команды действуют на устройство с активным звонком, включая телефон.
  Не отвечай, что не умеешь управлять микрофоном: сначала проверь доступные
  инструменты T3. Если инструмент недоступен или вернул ошибку, сообщи об этом;
  не утверждай, что действие выполнено.
- Голосом я прошу коротко («открой тред про маунт», «создай тред на горе»):
  сразу делай первое действие по таблице выше, не уточняй очевидное.

## T3 и воркспейсы

- Проекты в сайдбаре разложены по воркспейсам (плиткам). Главный — **main**:
  там идёт вся моя основная работа, там проекты и треды, которые прямо сейчас
  в центре моего внимания и ждут меня. Остальные воркспейсы (Personal, vtb,
  potentialplus…) — тематический архив, чтобы спокойно найти нужный проект;
  по ним я не хожу.
- Сам ничего в main не переноси и оттуда не убирай — только по моей просьбе.
  Воркспейс назначается проекту целиком (`t3ctl ws show <проект> main`),
  отдельный тред туда не положить; закреплённые треды видны во всех воркспейсах.
  Раскладка общая для всех машин.

## Инбокс T3: отчёты и вопросы мне

- Во встроенном инбоксе T3 Code я читаю всё, что требует моего внимания.
  Новости, вопросы и итоговые отчёты кладутся туда как issue, а не
  в новые треды и не в GitHub issues. Одна проблема или работа — один issue.
- Инструменты MCP `t3-code` (схемы проверяй в живом каталоге):
  - `inbox_post` (`severity`, `title`, `description` в markdown, `dedupeKey`,
    `waitingForOwner`, опционально `projectId`, `threadIds`) создаёт issue
    или обновляет существующий. Тред, из которого он вызван, становится
    ответственным: мои комментарии приходят в него с меткой
    `[T3 inbox · issue …]`. Повторный post с тем же `dedupeKey` обновит
    открытый issue или заново откроет закрытый, но дубликат не создаст.
  - `inbox_list` (`state`: open, resolved, dismissed или all; `severity`,
    `waitingForOwner`, `limit`) и `inbox_get` (`issueId`, вместе с историей)
    нужны для чтения. Перед post проверь, нет ли уже issue по этой работе.
  - `inbox_comment` (`issueId`, `text`, `waitingForOwner`) — ход работы и
    ответы на мои комментарии.
  - `inbox_update` (`issueId`; `title`, `description`, `severity`,
    `waitingForOwner`, `threadIds`, `responsibleThreadId`) обновляет
    описание и флаг. Через `responsibleThreadId` issue передаётся
    другому треду.
  - `inbox_resolve` (`issueId` или `dedupeKey`, `resolution`) закрывает
    issue только после проверки. В `resolution` напиши, как проверял.
- `severity`: `action` — нужно моё решение; `attention` — стоит посмотреть;
  `info` — отчёт для спокойного чтения. `waitingForOwner=true` ставь только
  тогда, когда без моего ответа правда не продвинуться. Этот флаг меняет
  только агент, моё прочтение его не снимает.
- Если я прошу отчёт о сделанной работе, issue `info` нужен даже при полном
  успехе: что сделано, до и после, как проверено, что осталось.
- CLI-запасной вариант (скилл `t3`): `t3ctl inbox post <action|attention|info>
  "Заголовок" --body MD --key KEY --project PROJECT [--waiting]`,
  `t3ctl inbox comment|update|done …`. Issue, созданный через CLI, остаётся
  без ответственного треда, поэтому из треда T3 предпочитай MCP.

# Global rules

## Python — ALWAYS via uv (critical)

- Never call `python`, `python3`, `pip`, `pip3`, `python -m venv` directly.
- Run scripts: `uv run script.py` (standalone scripts: PEP 723 inline deps + `uv run --script`).
- One-off code: `uv run python -c '...'` / `uv run --with <pkg> python -c '...'`.
- Tools: `uvx <tool>` or `uv tool run <tool>`.
- Projects: `uv add` / `uv remove` / `uv sync` / `uv run`. Dependencies: `uv pip install` only inside a uv venv, never system pip.
- Applies to skills, scripts, hooks and examples you write as well.
